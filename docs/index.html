2. What is a MicroLM (µLM)?

MicroLM (µLM) stands for Micro Learning Model — NOT Language Model.

Modern enterprise workflows have become over-reliant on monolithic, multi-billion parameter Large Language Models (LLMs). While generative LLMs excel at creative writing and brainstorming, utilizing them for developer workflows, policy gates, and local terminals introduces severe flaws: 500ms–3,000ms network roundtrips, cloud API bills, security egress risks, and unpredictable hallucination.

The MicroLM (µLM) Paradigm replaces heavy generalist chatbots with precision-crafted, task-dedicated neural engines:

Dimension Generative Chatbot LLM Nio MicroLM (µLM) Engine
Scope General-purpose conversational text Task-dedicated mathematical intelligence
Peak RAM 1,120 MB to several GBs < 47 MB to 86 MB (>92% to 95% reduction)
Footprint 7 Billion to 400+ Billion parameters 0.5M to 5.0M bounded parameters
Execution Cloud data centers (NVIDIA H100 clusters) In-process edge execution (Standard CPU / NPU)
Latency 300ms to 3,500ms per turn Sub-100µs to sub-5ms in-process
Outputs Ambiguous prose requiring regex parsing Deterministic structured verdicts & scores
Data Privacy Prompts leave machine to 3rd-party cloud Zero egress: 100% on 127.0.0.1 air-gapped
Cost Per-token API pricing & cloud subscriptions $0.00 forever (Zero API keys needed)

The 4 Universal Principles of MicroLMs (µLMs)

🎯

1. Task-Dedicated Intelligence

Models are trained with strict domain loss functions (multi-task cross-entropy, focal loss, calibrated MSE) rather than broad language prediction.

⚡

2. Sub-5ms In-Process Execution

Every engine is compiled to standard ONNX and executed natively via Rust (ort runtime) directly inside developer CLI processes and daemons.

🛡️

3. Absolute Data Sovereignty

No user code, file paths, private keys, or command lines ever leave localhost. Eliminates corporate data leak liabilities.

📐

4. Exact Parameter Budgeting

Every single parameter must earn its place. Models are engineered to exact bounds (e.g. 5,000,000 for Micro, 1,100,000 for Mask) to guarantee resident RAM constraints.

Nano is the embedded reflex layer of the Nio ecosystem. Embedded directly into native Rust binaries with zero external runtime dependencies, it acts as the initial filter in developer terminals, IDE extensions, and CLI daemons.

Technical Specifications

  • Parameters: ~500,000 (0.5M domain feature weights)
  • Latency: < 0.1ms (sub-100 microseconds) on single CPU core
  • Memory Footprint: ~5 MB resident RAM
  • Implementation: In-process Rust (nio-xs/crates/nano/src/model.rs)
  • Architecture: Multinomial feature matrix with n-gram tokenization and lexical intent routing.

Deterministic Intent Routing Classes

7. Micro — Domain-Clustered Decision Engine (5.0M / Cluster)

Micro (nioxs::micro) is the flagship decision engine of Nio. It serves as an autonomous, deterministic gatekeeper for code diffs, command executions, pull requests, and infrastructure operations.

The Modular Domain Cluster Architecture

Rather than ballooning one model into hundreds of millions of parameters—which causes cross-domain confusion and high memory footprints—Micro is architected as modular 5M ONNX engines.

Each cluster contains exactly 5,000,000 parameters and runs in under 5ms on standard CPUs. The runtime dynamically mounts the required cluster based on tool namespaces or context:

🛡️

Security Cluster (sec)

Audits security commands (semgrep, nuclei, trufflehog), private keys, Golden Ticket exploits, shadow reads, and token exposures.

⚙️

Base Workflow Cluster (base)

Evaluates standard developer workflows, Git operations, code modifications, build pipelines, and unit test changes.

micro_base.onnx (20 MB)
📈

Financial Cluster (fin)

Enforces algorithmic trading thresholds, FIX protocol gateways, margin risks, and clearing settlement invariants.

Transformer Architecture & Multi-Task Heads

  • Backbone: 4-Layer Bidirectional Transformer Encoder ($d_{\text{model}} = 224$, 4 Attention Heads, $d_{\text{ff}} = 1,304$).

9. Mini — Pre-emptive Defect Forecaster (7.1M)

Mini (nioxs::mini) is the pre-execution quality and safety engine of the Nio ecosystem. Trained on Abstract Syntax Tree (AST) diff hunks and dependency trees, it pre-emptively forecasts whether proposed code edits will break compilation, fail existing test suites, or induce runtime regressions before executing cargo test or triggering CI builds.

Architecture & Mathematical Budget

  • Parameter Count: Exactly 7,100,000 parameters ($d_{ ext{model}} = 256$, 6 layers, 8 heads, $d_{ ext{ff}} = 1,024$, $d_{ ext{break}} = 192$, $d_{ ext{cat}} = 167$, $d_{ ext{risk}} = 120$).
  • Core Backbone: 6-Layer Transformer Encoder with Graph AST Feature Projection.
  • Inference Latency: < 5ms on standard CPU without GPU acceleration.
  • Model Footprint: 27.14 MB standalone single-file ONNX binary (~28 MB resident RAM).

Multi-Head Output Payload

18. Frequently Asked Questions

What is a MicroLM (µLM) and how does it differ from a Large Language Model (LLM)?

MicroLM (µLM) stands for Micro Learning Model — NOT Language Model. Conventional Large Language Models (LLMs) have 7B to 400B+ parameters, run in distant GPU cloud data centers, incur 500ms–3,000ms network roundtrips, cost money per token, and generate unstructured conversational prose that can hallucinate. In contrast, Nio MicroLMs are compact (0.5M to 50M parameters), mathematically budgeted neural engines trained with exact domain loss functions. They execute 100% in-process on standard CPUs with sub-millisecond to sub-35ms latencies, produce deterministic structured verdicts, and cost $0.00 forever with zero cloud egress.

What performance has been verified for Viper?

On standard commodity x86_64 CPUs running the native pure-Rust AST-MicroLM runtime (nio-viper-runtime), Viper measures 11.70 MB initial engine RAM and reaches only 27.14 MB peak resident RAM (VmHWM). Prompt prefill completes in-process, and candidate sampling runs in sub-20 microseconds via tactical AST reflex projection. Quantized to Q4_0 GGUF (61.69 MB), it executes directly with zero Python or heavy external runtime overhead.

How does Viper enforce safety with its Destructive Safety Clutch and Swiss Gear?

Viper incorporates an active Destructive Safety Clutch that intercepts dangerous mutations (such as rm -rf, kill -9, git reset --hard, and systemd stops), requiring explicit interactive operator confirmation before execution. Additionally, Swiss Gear deterministic slot grounding extracts quoted literals and ports to eliminate parameter hallucination.

How do the NioXS CLI (`nioxs`) and NioAI CLI (`nio`) interact?

nioxs is the lightweight edge tensor runtime CLI. It manages model pulling (nioxs pull), verifies cryptographic SHA-256 checksums, caches weights in ~/.nioxs/models, and executes direct single-shot queries (e.g. nioxs viper "...", nioxs micro sec --diff "...", nioxs mini "...").
nio is the developer agent workspace CLI. It runs higher-level agentic workflows, orchestrating Nano directives (--bash, --tools), AST symbol indexers, and the Epistemic Triad delegation while utilizing nioxs models as local in-process co-processors.

How does Nano execute directives (`--`) with zero generative tokens spent?

When user input begins with -- (such as --bash cargo check, --tools generate-icons, or --callers ViperEngine), Nano's lexical AST interceptor short-circuits evaluation in < 0.05ms. It maps the directive directly to local subprocess execution or Tree-sitter symbol caches without querying any neural weights or sending packets over the network, saving 100% of generative tokens.

How does Mask scrub secrets at < 0.2ms without false positives on Git commit hashes?

Mask combines a 2-layer Byte-Level Convolutional Transformer ($K=5$) with a Shannon entropy scanner. Crucially, the training curriculum explicitly incorporates negative counter-examples (benign high-entropy tokens such as 40-character Git commit SHAs, UUIDs, and Docker image digests). This allows Mask to scrub AWS keys, GitHub tokens, passwords, and private SSH keys with 99.95% accuracy while preserving valid developer hashes with zero false positives.

How does Mini predict compiler and test failures before running `cargo test`?

Mini is a 7.1M parameter model trained on graph-projected Abstract Syntax Tree (AST) diff hunks and dependency hierarchies. In < 5ms, it produces a calibrated probability score (will_break) and classifies likely defect categories (e.g. BORROW_CHECK_FAIL, SYNTAX_ERROR, TYPE_MISMATCH, TEST_REGRESSION). This allows IDEs and pre-commit hooks to alert developers before slow build and test cycles run.

Why distribute ONNX instead of raw PyTorch checkpoints?

ONNX (Open Neural Network Exchange) is language-agnostic and runtime-agnostic. It runs directly inside native Rust, C++, Go, Python, and WebAssembly with zero Python runtime dependency, zero PyTorch overhead, and instant sub-millisecond execution on standard CPUs and NPUs via the native ort engine.

Why does Nio distribute models in both GGUF and ONNX formats?

Nio selects the optimal serialization format for each model's operational domain:
• ONNX: Used for discriminative policy, classification, stream redaction, and defect engines (Micro, Mask, Mini). ONNX enables multi-head tensor extraction with minimal latency and standard CPU/NPU hardware acceleration.
• GGUF: Used for autoregressive generative models (Viper). GGUF provides standardized 4-bit quantization (Q4_0), memory-mapped tensor loading, and tight integration with native Rust Candle kernels.

Can multiple Micro clusters run simultaneously in memory?

Yes. Because each cluster uses only ~35 MB resident RAM, running all three production clusters (sec, infra, and base) concurrently consumes less than 110 MB RAM total—well within the resident memory budget of any development machine or edge device.

How do Nio models guarantee 100% data sovereignty and zero cloud egress?

Every Nio model executes 100% locally on 127.0.0.1 inside user-controlled process memory. Zero telemetry, zero user code, and zero terminal commands are ever transmitted to third-party cloud servers. Nio models are fully functional in air-gapped environments without an active internet connection.

What hardware platforms and operating systems are supported?

All compiled binaries are cross-platform and support:
• x86_64: Linux (Ubuntu, Debian, Fedora, Arch, Alpine/musl), macOS (Intel), Windows 10/11.
• ARM64: Apple Silicon (M1/M2/M3/M4), Qualcomm Snapdragon X Elite, Raspberry Pi 4/5, and AWS Graviton servers.
No dedicated GPU is required; all models are optimized for standard commodity CPUs.
